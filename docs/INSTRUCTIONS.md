# INSTRUCTIONS — что это, зачем и как запускать

Полная инструкция по шаблону `teamwork-agent`: что внутри, как перенести в
свой проект, как работает каждый инструмент и что делать, когда что-то идёт
не так.

Уровень детализации рассчитан на человека, который будет настраивать это
в первый раз. После первой настройки достаточно раздела «Ежедневная работа».

## 1. Проблема, которую это решает

### 1.1 Что происходит без шаблона

Несколько агентов (Claude Code, Codex, Cursor, открытые терминалы с
агентными режимами, скрипты-автоматизации) правят один репозиторий
одновременно. Каждый из них достаточно умён и совершенно не видит остальных.

Типовые инциденты:

**Столкновение.** Два агента правят один файл. Оба считают его своим. Через
час правка второго перетирает правку первого. Оба записывают в свои отчёты
«сделано», тесты зелёные — потому что тестируют уже испорченный результат.
Самое дорогое здесь — не сломанный код, а **неверный отчёт**: агент
объявляет задачу выполненной, и никто не узнаёт, что она не сделана.

**Дедлок.** Агент видит «файл занят зоной `pipeline`, владелец — helios» и
ждёт. `helios` давно закончил и ушёл. Ожидание не имеет конца, потому что
его нечему разблокировать: владелец не вернётся, а зона осталась занятой
навсегда.

**Замёрзший журнал.** Правило «журнал статуса пишет один назначенный агент»
работает ровно до момента, когда этот агент отключается. Дальше **никто**
не может отметить свой claim, потому что право есть только у него. Правило
исполняемо и проверяемо — и именно поэтому оно опасно: дедлок выглядит как
строгое соблюдение регламента.

**Потерянные записи.** Два агента открыли `.agent-handoff.json`, оба
внесли правку, оба записали. Один потерял работу другого. Никто не заметил:
просто в журнале стало на одну запись меньше.

### 1.2 Как это решается конструктивно

| Инцидент | Конструкция, которая его исключает |
|---|---|
| Столкновение | Владение = **живой claim на файл**. `who-owns` и `claim` спрашивают про конкретный путь, а не про зону |
| Дедлок | Claim **протухает** через 90 минут без heartbeat, и его файлы освобождаются сами |
| Замёрзший журнал | Журнал **self-service**: каждый пишет `agents.<свой-имя>.*`; назначенного писателя нет |
| Потерянные записи | Единственный writer с атомарной записью: `read → modify → validate → atomic replace` |

Каждая строка здесь — следствие конструкции, а не договорённость. Поэтому
правила нельзя «немного нарушить»: нарушение восстанавливает ровно ту
поломку, ради устранения которой всё и затевалось.

### 1.3 Чего шаблон не делает

Честный список, чтобы не искать:

- **Не разрешает конфликт мнений.** Если два агента считают правильными
  разные архитектуры, шаблон не поможет. Для этого `docs/rfc/`.
- **Не заменяет CI.** Гейты запускаются локально. Шаблон содержит workflow
  для GitHub Actions, но гейт в CI и гейт у агента — разные вещи: CI
  ловит регрессию после мержа, локальный гейт — до.
- **Не ограничивает число агентов технически.** `claims.max_agents` —
  договорённость, а не блокировка. Это осознанно: блокировка означала бы
  ровно то зависание, которое шаблон устраняет.
- **Не знает вашего проекта.** Схема признаков, API-контракты, модель данных
  — их в шаблоне нет по определению. Их вносит владелец проекта в
  `contracts_easy_to_break`.

## 2. Архитектура: три файла и почему именно три

### 2.1 Разделение

```
.agent-protocol.json      ПРАВИЛА      меняет владелец проекта
        ↓ читается
.agent-handoff.json       СОСТОЯНИЕ    пишут все агенты
        ↓ читается
docs/agent-status.json    СНИМОК       пишут все агенты
        ↓ отображается
scripts/agent_dashboard.py             read-only
```

Правила и состояние разведены намеренно. Первая версия шаблона держала
правила в двух файлах, и когда они расходились, невозможно было понять,
какой текст главный. Правило «при расхождении верь более свежей правке»
неисполнимо: у JSON нет времени, есть только `mtime`, и он не отвечает на
вопрос о смысле.

### 2.2 Кто что пишет

| Файл | Кто пишет | Чем |
|---|---|---|
| `.agent-protocol.json` | Любой агент | `protocol-set`, `backlog add/set` |
| `.agent-handoff.json` | Любой агент | `claim`, `release`, `heartbeat`, `log-entry`, `hint` |
| `docs/agent-status.json` | Любой агент | `status-set` |

**Ручные правки запрещены.** Не из эстетики: `write_json_atomic` делает
`read → modify → проверка mtime → сериализация → валидация → os.replace`.
Ручная правка через редактор проходит мимо всех шести шагов и может
уничтожить запись, сделанную в это же время.

### 2.3 Почему три, а не один файл

Файл состояния переписывается десятки раз в день. Файл правил — раз в
несколько недель. Совмещать их значит: при каждой записи claim переписывать
протокол (риск испортить), и при каждом обновлении протокола рисковать
потерять живой claim. Разделение убирает обе возможности структурно.

## 3. Модель владения

### 3.1 Три уровня, из которых только один блокирует

```
Файл занят?   ──▶ живой claim на этот файл?   ──▶ ДА: занято, бери другую задачу
                        │
                       НЕТ
                        ▼
                 Файл свободен. Бери.
```

Зона — **подсказка**: она показывает, где обычно работают, чтобы не
пересечься. Зона никогда не блокирует. Отсутствие зоны тоже не блокирует —
это не повод ждать.

### 3.2 Протухание — механизм против тупика

```
claim создан ──► работа ──► heartbeat каждые 30 мин
                        │
                   (агент исчез)
                        │
                        ▼
            90 минут без heartbeat
                        │
                        ▼
              claim = БРОШЕННЫЙ
              файлы СВОБОДНЫ
```

`status` помечает такие claims как `[УСТАРЕЛ — файлы свободны]`, `who-owns`
перестаёт считать файлы занятыми, `claim` их выдаёт.

Единственное исключение: если у claim **нет** метки времени, он считается
свежим. Это асимметрия намеренная — при сомнении лучше не отнять чужую
работу.

### 3.3 Перезапущенная сессия — не второй агент

Если `claim` отказывает с кодом 4 и говорит, что имя уже держит живой
claim, — почти всегда это перезапуск сессии, а не новый агент.

Молча взять то же имя опаснее, чем подождать: claim первой сессии заменяется,
её файлы перестают защищаться детектором конфликтов, а первая сессия
продолжает их править. Никто этого не видит — просто набор занятых файлов
уменьшается.

Правильно: имя вида `<твоё-имя>/2`. Для случая «первая сессия точно мертва» —
флаг `--take-over`, и об этом нужно написать в `coordination_note`.

### 3.4 Зона `reserved`

Единственная настоящая огороженная территория: там, где ошибка ломает то,
что **вне репозитория** — настройки ОС, миграции боевой базы, деплой,
секреты. Claim требует явного `--force`.

**В свежем шаблоне список пуст, и это правильное состояние.** Придумывать
резервацию без реальной опасности вредно: лишний запрет блокирует агентов
без причины и приучает их обходить `--force`.

## 4. Установка в свой проект

### 4.1 Вариант A — копирование (рекомендуется)

Координация — часть репозитория. Она обязана жить в том же коммите, что и
код, который координирует: установленный пакет «где-то» через неделю
разъедется версиями.

```bash
# Из клона шаблона
git clone <url> /tmp/tw

cd /path/ваш/проект

cp /tmp/tw/.agent-protocol.json   .
cp /tmp/tw/.agent-handoff.json    .
mkdir -p docs scripts
cp /tmp/tw/docs/agent-status.json docs/
cp /tmp/tw/docs/AGENT_PROMPT.md   docs/
cp /tmp/tw/docs/TEAM_PROTOCOL.md  docs/
cp /tmp/tw/docs/PROJECT_STATUS.md docs/
cp /tmp/tw/scripts/agent_handoff.py scripts/
cp /tmp/tw/scripts/dev.py           scripts/
cp /tmp/tw/scripts/gates.example.json scripts/gates.json

# Документация — по желанию
cp /tmp/tw/README.md               README_COORDINATION.md
cp /tmp/tw/Makefile                Makefile.coordination
mkdir -p docs/rfc && cp /tmp/tw/docs/rfc/*.md docs/rfc/
```

Тесты шаблона можно положить в `tests/coordination/` — они проверяют сам
инструмент, а не ваш код, и остаются зелёными при любых ваших изменениях.

**Ничего не удаляйте из `scripts/agent_handoff.py`.** Файл переписан целиком
при первом конфликте, и координация откатывается в состояние «все всё
делают, никто ничего не видит».

### 4.2 Вариант B — установка как зависимость

```bash
python -m pip install -e ".[all]"    # pytest, ruff, fastapi, uvicorn
python -m pip install -e ".[dev]"    # только pytest, ruff
python -m pip install -e ".[dashboard]"
```

Подходит, если вы держите несколько репозиториев на одной координации.
Минус: версия инструмента одна на всех, а правила живут в каждом
репозитории отдельно — и рассинхронизация инструмента с протоколом
возможна.

### 4.3 Вариант C — git submodule

```bash
git submodule add <url> .teamwork
python .teamwork/scripts/agent_handoff.py status
```

Плюс: обновляется централизованно. Минус: путь к скрипту становится длинным,
и координационные файлы всё равно лежат в вашем репозитории.

### 4.4 Проверка установки

```bash
python scripts\agent_handoff.py validate     # ожидается код 0
python scripts\agent_handoff.py health-check # ожидается код 0
python scripts\dev.py doctor
python -m pytest -q
```

Если `validate` даёт код 1 — читайте блок `проблемы (N)`. Каждая строка там
указывает конкретный файл и конкретную причину.

### 4.5 Что НЕ копировать

| Не копировать | Почему |
|---|---|
| `.venv/`, `__pycache__/` | Среда, не код |
| `.agent-events.jsonl` | Сырой поток событий, большой и не нужный |
| `.agent-handoff.backups/` | Бэкапы `repair-encoding`, восстанавливаемы |
| `.gitattributes` без проверки | Если в проекте уже есть свой — **объедините**, а не перезапишите: чужой `* text=auto eol=crlf` наоборот поломает JSON |
| `tests/test_gitignore.py` | Проверяет `.gitignore` **вашего** проекта; настройте свой список |
| `tests/test_dev_gates.py` целиком | Часть тестов — про гейты вашего проекта; оставьте контрактные, перепишите проектные |

### 4.6 О `.gitattributes` отдельно

Файл нормализует переводы строк. Это не косметика: координационные файлы
переписываются агентами на разных системах, и без нормализации checkout на
Windows переписывает их в CRLF, а wsl-агент пишет обратно в LF — после чего
`git diff` показывает изменение каждой строки файла, который никто не менял.

**Если в вашем проекте уже есть `.gitattributes`** — не перезаписывайте.
Возьмите из шаблона только правила для `*.py`, `*.json`, `*.md` и двоичных
типов, сохранив существующие правила. Особенно осторожно с `*.bat`/`*.ps1`:
там CRLF обязателен, а для всего остального в вашем проекте может быть
наоборот верным CRLF.

## 5. Что обязательно заполнить в протоколе

Это единственная часть работы по настройке, без которой шаблон формально
работает, а по сути бесполезен. Агент не будет ждать, что вы это сделали:
он начнёт работать и сломает то, что нельзя.

### 5.1 `zones` — карта областей

```jsonc
"zones": {
    "api":     ["src/api/", "tests/test_api.py"],
    "storage": ["src/db/", "migrations/"],
    "frontend": ["web/", "src/ui/"],
    "infra":   ["deploy/", "terraform/"],
    "reserved": ["migrations/"],
    "free":    ["README.md", "Makefile"]
}
```

**Как.** Возьмите верхние 1–2 уровня дерева исходников и сгруппируйте по
компонентам. Цель — чтобы агент на вопрос «где здесь граница?» мог ответить
за секунду. Не дробите на зоны по одной строке: зон меньше пяти.

**Чего не делать.** Не добавлять имена агентов. Не указывать файлы, которых
нет. Не делать зоны обязательными — они не блокируют.

### 5.2 `verification` — команды гейтов

```jsonc
"verification": {
    "minimum": "python -m pytest -q",
    "end_to_end": "python scripts/e2e_check.py",
    "before_claim": "Run pytest FIRST so you know the baseline before your change."
}
```

Полный список гейтов — в `scripts/gates.json`:

```json
[
  {"name": "pytest",    "args": ["-m", "pytest", "-q"], "note": "все тесты"},
  {"name": "lint",      "args": ["-m", "ruff", "check", "."], "note": "стиль"},
  {"name": "coordination", "args": ["scripts/agent_handoff.py", "validate"],
   "note": "целостность coordination-файлов"},
  {"name": "e2e",       "args": ["-u", "scripts/e2e_check.py"],
   "note": "путь данных от входа до результата"},
  {"name": "real_data", "args": ["-u", "scripts/check_real_data.py", "--limit", "1000"],
   "note": "на реальных данных", "requires": "data/*.csv"}
]
```

Ключ `requires` — glob входных данных. Нет данных → `SKIP`, а не падение.

### 5.3 `contracts_easy_to_break` — самый ценный раздел

Это то, что читает новый агент, чтобы понять, куда нельзя лезть. Пустой
раздел означает, что каждый агент заново открывает ваши ошибки.

```jsonc
"contracts_easy_to_break": {
    "User schema": "Миграции в src/db/migrations/. Изменение набора полей — "
                   "только с новой SCHEMA_VERSION и обратной совместимостью. "
                   "Закреплено tests/test_migrations.py.",
    "-1 sentinel": "-1 в metrics означает 'не проверено', а не 'ноль': бюджеты "
                   "проверок общие на прогон. Ранжирование обязано трактовать "
                   "как 'неизвестно', иначе неповеренное становится чистым. "
                   "Закреплено tests/test_budget_semantics.py.",
    "Public API": "GET /users отдаёт snake_case. Клиенты на camelCase "
                  "ломаются молча — переименование требует версии."
}
```

**Формат каждой записи:** что это · что ломает · какое действие требуется ·
**какой тест это закрепляет**. Последнее обязательно: контракт, не
закреплённый тестом, разрушается в том же коммите, который его нарушил.

**Типовые кандидаты**, которые стоит проверить у себя:

- Схема данных и версионирование схемы.
- Sentinel-значения (`-1`, `null`, `0`) и разница между «не проверено» и
  «не применимо».
- Границы компонентов: что пишет один и что читает другой по именам.
- Публичный API и его потребители.
- Порядок, который неявно важен (словари, на которые ссылаются тесты).
- Формат файлов на диске, если они переживают перезапуск.

### 5.4 `boundaries` — где ломается машина

```jsonc
"boundaries": {
    "test_ports": "В тестах port=0. Ручные серверы: 18900-18999. "
                  "API и воркер — разные порты.",
    "caches": "Тесты пишут в tmp_path. Runtime-БД никогда не используется "
              "как тестовый кэш.",
    "never_commit": [".venv/", "*.db", ".scratch/*", "build/", "*.egg-info/"],
    "scratch_prefixes": ["tmp", ".scratch", "_e2e_"],
    "temp_trap": "Проверь python -c \"import tempfile; print(tempfile.gettempdir())\"..."
}
```

**Проверьте `temp_trap` у себя** — это стоит три секунды и спасает от
мусорных каталогов во всём репозитории:

```bash
python -c "import tempfile; print(tempfile.gettempdir())"
```

Если выводится корень вашего репозитория — любой `mkdtemp()` без `dir=`
создаст папку прямо в рабочей копии, и она уедет в коммит вместе с
мусором. Лечится созданием папок явно (`.scratch/<агент>/<задача>/`) и
удалением в `finally`.

### 5.5 `reserved_rules` — что реально огорожено

Пустой список `zones.reserved` — валидное состояние. Заполняйте, только
если ошибка в зоне ломает систему **вне репозитория**.

Порядок работы с резервной зоной: записать своё имя в `zones.reserved`
протокола → предупредить команду через `hint` → взять с `--force` →
упомянуть в `coordination_note`.

### 5.6 `normalisation.author_markers`

Список имён для `normalize-legacy`. По умолчанию пуст, и тогда словарь
берётся из авторов, уже присутствующих в `task_log`. Заполнять нужно, только
если в старых записях имена выглядят как `... by Alice`.

## 6. Справочник команд

Все команды работают из корня репозитория. Если `python` недоступен —
используйте интерпретатор вашего venv.

### 6.1 Наблюдение

```bash
python scripts\agent_handoff.py status
```
Кто держит claim, сколько живых из скольких, зоны с пометкой занятых
файлов, все подсказки. Первый вызов нового агента.

```bash
python scripts\agent_handoff.py who-owns src/app.py src/db/
```
`ЗАНЯТО` — есть живой claim. `СВОБОДНО` — бери. Зона в ответе —
подсказка, а не запрет. Код возврата 1, если хоть один файл занят, — это
удобно для скриптов.

```bash
python scripts\agent_handoff.py backlog list
```
Приоритеты P0–P4 из протокола. Код 1, если есть открытый P0: не начинать
новых задач.

### 6.2 Claim

```bash
python scripts\agent_handoff.py claim "my-agent" "починить парсинг дат" \
    --files "src/parser.py,tests/test_parser.py"
```

| Флаг | Смысл |
|---|---|
| `--force` | Взять файл под чужим claim'ом. Только для **протухших**; описать в `coordination_note` |
| `--take-over` | Забрать живой claim с тем же именем. Почти всегда ошибка; правильно — имя `<имя>/2` |

Коды возврата: `0` — ок, `4` — отказ (занято живым claim'ом / своё имя уже
занято / reserved-зона без `--force`). Текст отказа объясняет, что делать.

### 6.3 Heartbeat и release

```bash
python scripts\agent_handoff.py heartbeat "my-agent" --note "тесты падают"
python scripts\agent_handoff.py release "my-agent"
```

Heartbeat обязателен после 30 минут. `release` — **всегда**, даже если
задача не удалась: claim протухнет, но оставит чужой `health-check`
красным на 90 минут.

### 6.4 Запись результата

```bash
python scripts\agent_handoff.py log-entry --agent "my-agent" --file entry.json
```

```json
{
  "date": "2026-10-10",
  "task": "починить парсинг дат",
  "author": "my-agent",
  "status": "DONE",
  "description": "причина бага и почему решение именно такое",
  "changed_files": ["src/parser.py", "tests/test_parser.py"],
  "verification": "python -m pytest -q tests/test_parser.py",
  "result": "14 passed (было 2 failed)",
  "next_agent_hint": "обязательно, если status != DONE",
  "coordination_note": "владение, конфликты, договорённости"
}
```

`description` важнее `result`. Через месяц результат можно воспроизвести, а
причину — нет. Команда идемпотентна: повторная запись с тем же `task`
пропускается.

### 6.5 Подсказки

```bash
python scripts\agent_handoff.py hint "To all: поменял API, /users теперь отдаёт limit"
python scripts\agent_handoff.py hint --remove "точная строка подсказки"
```

Одна мысль на строку, адресат в начале. Устаревшую подсказку **удаляйте**:
агент прочитает её и будет строить план по неверной информации.

### 6.6 Статус

```bash
python scripts\agent_handoff.py status-set agents.my-agent.status DONE --agent my-agent
python scripts\agent_handoff.py status-set current_gate '{"pytest": {"status": "passed", "result": "102 passed"}}' --agent my-agent
```

Пишите свой раздел. Чужой (`agents.<кто-то-другой>.*`) — код 4. Чтобы
исправить слот завершившейся сессии: `--force`. Чтобы перезаписать **живой**
слот: `--force --override-live`, и прежнее значение будет напечатано.

### 6.7 Обслуживание

```bash
python scripts\agent_handoff.py validate       # целостность, код 1 = блокирует
python scripts\agent_handoff.py health-check   # P0/P1, stale, кодировка, мусор
python scripts\agent_handoff.py repair-encoding --dry-run
python scripts\agent_handoff.py normalize-legacy
python scripts\agent_handoff.py protocol-set <ключ> '<json>'
python scripts\agent_handoff.py backlog add --priority P1 --area api --description "..."
python scripts\agent_handoff.py backlog set --id P1-001 --status done
```

## 7. Ежедневная работа

### 7.1 Агент

```
1. Прочитать .agent-handoff.json, .agent-protocol.json, docs/agent-status.json
   и contracts_easy_to_break из протокола.

2. Снять baseline: pytest -q ДО правок.
   Красное до правок — не твоя регрессия, и это надо запомнить.

3. status + who-owns по целевым файлам.

4. claim на одну задачу. Один claim — одна проверяемая задача.

5. Править атомарно. Чужой файл перечитывать НЕПОСРЕДСТВЕННО перед записью.

6. heartbeat каждые 30 минут на длинных задачах.

7. Гейты после правок.

8. log-entry с измеренными числами.

9. status-set для своего раздела.

10. release и удаление scratch.
```

Шаги 8–10 не формальность. Без них следующий агент не знает, что сделано,
`health-check` остаётся красным, а claim следующих 90 минут висит на файлах,
которые уже никто не трогает.

### 7.2 Владелец проекта

Раз в неделю, 10 минут:

```bash
python scripts\agent_handoff.py health-check
python scripts\agent_handoff.py backlog list
```

- Закрыть `done` в backlog, когда задача действительно сделана.
- Проверить, не копится ли `task_log` — каждый агент добавляет запись, файл
  растёт монотонно. При >200 записей имеет смысл архивировать старые в
  `docs/task_log_archive/`.
- Прочитать открытые `hints` и удалить устаревшие.
- Раз в месяц: сверить цифры в `PROJECT_STATUS.md` с реальным прогоном.

## 8. Гейты

### 8.1 Что даёт раннер

```bash
python scripts\dev.py gates          # все гейты + сводка
python scripts\dev.py gates --list   # только состав, ничего не запускает
```

Четыре свойства, ради которых раннер и написан:

1. **Прогон не останавливается на первом падении.** Иначе остальные гейты
   остались бы непроверенными, а «прогнал гейты» означало бы «увидел первое
   красное и ушёл».
2. **Красный гейт перезапускается один раз.** «Красный → зелёный»
   называется `МЕРЦАНИЕ`, даёт код 0 и громкое предупреждение в stderr.
   Причина почти всегда одна: файл правит другой агент прямо во время
   прогона.
3. **`МЕРЦАНИЕ` ≠ «всё хорошо».** Если тест падает у вас постоянно — это
   регрессия, а не мерцание.
4. **`SKIP` ≠ успех.** Гейт без входных данных показывается отдельно, а
   итоговая строка называет прогон `НЕПОЛНАЯ`.

### 8.2 Коды возврата

| Код | Значение |
|---|---|
| 0 | Все гейты зелёные (возможны мерцания — с предупреждением) |
| 1 | Есть устойчиво красные гейты |
| 0 + `НЕПОЛНАЯ` | Часть гейтов пропущена: отсутствуют входные данные |

### 8.3 В CI

Файл `.github/workflows/gates.yml` — готовая копия. Он запускает все гейты
на каждом пуше. Одна джоба, без `continue-on-error`: разделять быстрые и
тяжёлые гейты значит прятать настоящие падения.

Замена на другую CI: замените шаг `python scripts/dev.py gates` на
эквивалент вашей системы.

## 9. Дашборд

```bash
python scripts\agent_dashboard.py
# http://127.0.0.1:18900
```

Нужен `pip install ".[dashboard]"`.

Показывает: агентов и их статусы, claims с файлами, P0/P1, hints, последние

**Принципиально: дашборд никогда не пишет в coordination-файлы.** Это

всех эндпоинтов. Нарушение этого свойства превратило бы дашборд во второго
писателя журнала — то есть вернуло бы ровно те поломки, которые шаблон
устраняет.

Health score — число, придуманное дашбордом. У него нет калибровки.
Смотрите на исходные счётчики рядом с ним.

## 10. Как это ломается и что делать

### 10.1 Частые поломки

| Симптом | Причина | Лечение |
|---|---|---|
| `claim` даёт код 4 на свободный файл | Твоё имя держит живой claim (перезапуск сессии) | Возьми имя `<имя>/2` |
| Агент ждёт, хотя файлы свободны | Смотрит зону вместо `who-owns` | Зона не блокирует. Обучить на `who-owns` |
| Журнал не обновляется | Агент не знает про `status-set` | Добавить `hint`, проверить `docs/AGENT_PROMPT.md` |
| `validate` красный, ничего не менял | Накопленный шум: битый JSON, mojibake, несуществующие зоны | `repair-encoding`; поправить зоны |
| Кириллица в выводе — мусор | Файл сохранён не в UTF-8 | `repair-encoding`; читать как `utf-8-sig` |
| В корне появились папки `tmp*` | Сработала ловушка `temp_trap` | Проверить `tempfile.gettempdir()`, чинить вызовы `mkdtemp` |
| Дашборд не запускается | Нет `fastapi` | `pip install ".[dashboard]"`. Работа без него не блокируется |
| Гейт мигает красным-зелёным | Другой агент правит файл во время прогона | Это `МЕРЦАНИЕ`, код 0. Если падает постоянно — это ваша регрессия |
| Гейт `SKIP` | Нет входных данных | Создайте данные; `SKIP` — не успех |
| В `.gitignore` пропали `docs/agent-status.json` | Правило для `.agent-*` слишком широкое | Вернуть: coordination обязана быть в коммите |

### 10.2 «Всё сломалось, как откатить»

Координационные файлы — обычные файлы под git. Откат:

```bash
git checkout HEAD~1 -- .agent-protocol.json .agent-handoff.json docs/agent-status.json
```

Но сначала поймите, что именно сломалось: `git diff` покажет, кто и когда
трогал. Чаще всего виноват один неудачный `status-set --force --override-live`.

### 10.3 Чего не делать

- **Не редактировать координационные файлы руками.** Только через
  `agent_handoff.py`.
- **Не добавлять имена агентов в зоны.** Ушедший агент заблокирует область
  навсегда.
- **Не заводить «владельца журнала».** Это блокировка, которая выглядит как
  порядок.
- **Не использовать `--force` на живом claim'е.** Для этого есть
  `--override-live` у `status-set` и `--take-over` у `claim`.
- **Не удалять `tests/test_template_universality.py`,** если собираетесь
  обновлять шаблон: это единственное, что ловит проектные хвосты.
- **Не цитировать цифры из `PROJECT_STATUS.md`, не проверив их прогоном.**
  Отменённые числа должны быть помечены, а не стёрты.

## 11. Настройка под другие языки и стеки

### 11.1 Инструмент

`agent_handoff.py` и `dev.py` — **чистая стандартная библиотека Python
3.10+**. Их не нужно адаптировать под язык вашего проекта. Нужен только
интерпретатор Python.

### 11.2 Гейты

Гейт — это любая команда с кодом возврата. Для другого стека:

```json
[
  {"name": "tests_go",  "args": ["-m", "pytest", "-q", "tests/go"],
   "note": "тесты Go-части"},
  {"name": "tests_js",  "args": ["npm", "test"],
   "note": "тесты фронтенда"},
  {"name": "cargo",     "args": ["cargo", "clippy", "--", "-D", "warnings"],
   "note": "линтер Rust"},
  {"name": "coordination", "args": ["scripts/agent_handoff.py", "validate"],
   "note": "целостность coordination-файлов"}
]
```

Для не-Python гейтов замените `[py(), *gate.args]` на `[*gate.args]` в
`scripts/dev.py` — или задайте `python` первым элементом `args`, если
команда начинается с интерпретатора.

### 11.3 Для не-Python стека: раннер на Python или на вашем языке?

**Оставляйте `agent_handoff.py` на Python.** Причины измерены, а не
вкусовые:

- Атомарная запись — 60 строк с `os.replace` и проверкой `mtime`. В Rust или
  Go это тот же код плюс сборка бинарника, который агентам придётся ставить.
- В вашем репозитории **уже есть** Python? Не обязательно. Но он есть у
  вас на машине — иначе вы бы не читали этот документ.
- Агент, который знает Python, запустит инструмент. Агент, которому нужно
  сначала `make build-tools`, — не запустит, и координация не заработает.

Если Python в проекте категорически нет — портируйте `agent_handoff.py`,
но **сохраните всю семантику**: `utf-8-sig` при чтении, проверка `mtime`
перед записью, `os.replace`, `exit code 4` на отказ. Это и есть контракт.

## 12. Обслуживание шаблона

### 12.1 Правило «хвостов проекта»

Главная угроза шаблону — не поломка, а **незаметное обрастание проектной
спецификой**: путь, команда или имя из исходного проекта, ставшее частью
кода. Шаблон перестаёт работать в другом репозитории и выглядит при этом
целым.

Защита встроена: `tests/test_template_universality.py` падает, если в
`scripts/` появляется имя проекта-источника, его путь или имена его агентов.

**При обновлении шаблона в реальном проекте:** если вы добавили в
`agent_handoff.py` что-то про свой проект — это баг. Проектные вещи живут в
протоколе, а протокол машина читает.

### 12.2 Как добавить гейт в чужой проект

1. Добавить объект в `scripts/gates.json`.
2. `python scripts\dev.py gates --list` — состав обновился.
3. `python scripts\dev.py gates` — гейт запустился.
4. Внести описание гейта в `docs/PROJECT_STATUS.md` раздел 9.

Правки кода при этом не нужны, и это не совпадение: список гейтов —
конфигурация, а раннер — механизм.

### 12.3 Как перенести изменения шаблона в уже настроенный проект

```bash
cp /tmp/tw/scripts/agent_handoff.py   /path/проект/scripts/
cp /tmp/tw/scripts/dev.py             /path/проект/scripts/
cp /tmp/tw/tests/test_agent_handoff.py /path/проект/tests/
python -m pytest -q tests/test_agent_handoff.py
```

Не копировать `.agent-protocol.json` и `.agent-handoff.json`: там ваши зоны,
гейты, контракты и история. Копируются **механизмы**, не состояние.

### 12.4 Как проверить, что шаблон не потерял форму

```bash
python -m pytest -q -k universality
```

Ноль пройденных тестов здесь означает, что файл проверок удалён. Это
хуже, чем красные тесты: без него проектные хвосты возвращаются
незаметно.

## Приложение: быстрая памятка

```bash
# Наблюдение
python scripts\agent_handoff.py status
python scripts\agent_handoff.py who-owns <файл>
python scripts\agent_handoff.py backlog list

# Работа
python scripts\agent_handoff.py claim "<ты>" "<задача>" --files <файлы>
python scripts\agent_handoff.py heartbeat "<ты>" --note "прогресс"
python -m pytest -q
python scripts\dev.py gates
python scripts\agent_handoff.py log-entry --agent "<ты>" --file entry.json
python scripts\agent_handoff.py status-set agents.<ты>.status DONE --agent "<ты>"
python scripts\agent_handoff.py release "<ты>"

# Проверка шаблона
python scripts\agent_handoff.py validate        # код 0 = цело
python scripts\agent_handoff.py health-check    # код 0 = чисто
python -m pytest -q -k universality              # шаблон не оброс хвостами
```

Пять правил, которые важнее остальных:

1. **Файл занят только живым claim'ом.** Зона не блокирует.
2. **Claim протухает через 90 минут.** Не жди того, кто не придёт.
3. **Пиши координационные файлы только через `agent_handoff.py`.**
4. **Красный гейт — работа не сдана.** `SKIP` — тоже не сдана.
5. **Всегда `release`.** Claim без heartbeat исчезнет сам через 90 минут, но
   до тех пор `health-check` будет красным.
