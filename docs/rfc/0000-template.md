Когда RFC пишется: изменение затрагивает больше одной зоны, меняет публичный
контракт, добавляет зависимость, или есть **два разумных варианта**, и
записывать в `task_log` придётся не факт, а решение.

Что **не** требует RFC: очевидная правка внутри одной зоны, багфикс,
рефакторинг без изменения поведения. Для этого есть `claim` + `log-entry`.

## Контекст

Что сейчас не так. Только факты и, если есть, замеры. Без решения в этом
разделе.

## Проблема

Почему текущее поведение неприемлемо. Кто и как страдает.

## Варианты

Минимум два. Один вариант — это не выбор, это предложение закрыть вопрос.

| | Вариант A | Вариант B |
|---|---|---|
| Суть | | |
| Плюсы | | |
| Минусы | | |
| Что ломает | | |
| Стоимость | | |

**Замер, а не мнение.** Если варианты выбираются по скорости, памяти или
точности — приведи числа с командой, условиями и датой. «Кажется, что A
быстрее» не является аргументом; оно снимается одним прогоном.

## Решение

Что выбрано и **почему**. Ссылка на измерение, если выбор был по числам.

Здесь же: что выбранный вариант сознательно **не** делает.

## Последствия

- Что ломается для пользователей.
- Что нужно мигрировать.
- Что становится запрещённым после этого (новое правило в
  `contracts_easy_to_break`).
- Как проверить, что изменение сработало.
