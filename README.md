# teamwork-agent

**Шаблон для того, чтобы несколько ИИ-агентов работали в одном репозитории как команда, а не как стихийное бедствие.**

Проверено на практике: пять агентов, один проект, один день — и ни одного
разговора «а ты это уже правил?».

```
python scripts\agent_handoff.py status      # кто чем занят прямо сейчас
python scripts\dev.py gates                 # все проверки разом + сводка
python scripts\agent_dashboard.py           # http://127.0.0.1:18900
```

Ядро работает на **чистой стандартной библиотеке Python**. `pip install` не
нужен. Ничего не ломается, если у вас в проекте нет venv, нет ruff и нет
веб-фреймворка.

```bash

python scripts\agent_handoff.py validate
```

Подробности — в **[docs/INSTRUCTIONS.md](docs/INSTRUCTIONS.md)**. Это
«инструкция на 12 экранов»: что заполнить в своём проекте, справочник всех
команд, что делать, когда что-то сломалось.

А если вы уже знаете, как это устроено, и просто хотите промпт для нового
агента — берите **[docs/AGENT_PROMPT.md](docs/AGENT_PROMPT.md)** и
отправляйте целиком. Он самодостаточен.

## О чём этот шаблон на самом деле

Чтобы не было недоразумения: это **не** библиотека и **не** фреймворк.
Это соглашение плюс инструмент, который делает соглашение исполнимым.

### Проблема, которую он решает

Агенты достаточно умные. Они при этом **совершенно не видят друг друга**.

И вот что из этого получается.

**Столкновение.** Два агента правят один файл. Оба уверены, что файл их.
Через час правка второго перетирает правку первого. Оба пишут в отчёт
«сделано». Тесты зелёные — потому что проверяют уже испорченный результат.
Самое дорогое здесь не сломанный код. Самое дорогое — **неверный отчёт**:
задача объявлена выполненной, и никто об этом не узнает.

**Дедлок.** Агент видит: «файл занят зоной `pipeline`, владелец — Вася».
Ждёт. Вася закончил два часа назад и ушёл. Ожиданию нечему закончиться,
потому что разблокировать его некому: Вася не вернётся, а зона занята
навсегда. И это самый неприятный сценарий, потому что выглядит он как
строгое соблюдение регламента.

**Замёрзший журнал.** Правило «журнал статуса пишет один назначенный
агент» работает идеально — ровно до момента, когда этот агент
отключается. Дальше **никто** не может отметить свой claim, потому что
право есть только у него. И никто этого не замечает: журнал просто
перестаёт меняться.

**Потерянные записи.** Два агента открыли один JSON, оба внесли правку,
оба записали. Один потерял работу другого. Никакого сообщения об ошибке —
просто в журнале стало на одну запись меньше.

### Как это перестаёт повторяться

Каждая строка ниже — следствие конструкции, а не договорённость. Поэтому
нарушить её нельзя случайно: нарушение возвращает ровно ту поломку,
ради устранения которой всё затевалось.

| Проблема | Что мешает |
|---|---|
| Столкновение | Владение определяет **живой claim на конкретный файл**, а не имя агента и не зона |
| Дедлок | Claim без heartbeat 90 минут считается брошенным, и файлы освобождаются **сами** |
| Замёрзший журнал | Журнал **self-service**: каждый пишет свой раздел `agents.<своё-имя>.*`. Назначенного писателя нет |
| Потерянные записи | Единственный инструмент записи, и он атомарный: `read → modify → проверка mtime → валидация → os.replace` |

**Про зоны — потому что это главное misunderstanding.** Зона описывает
*область кода*, а не *человека*. Она нужна, чтобы понять «где я, а где
коллега». Она **никогда не блокирует**. Если ваш файл не попал ни в одну
зону — это не повод ждать, берите его.

Старая схема, где зона закреплена за именем агента, ломалась так: агент
уходил — и зона становилась недоступной для всех навсегда. Новый агент
приходил, видел «занято» и честно ждал того, кто не придёт.

**Про перезапущенную сессию.** Если `claim` отказал с кодом 4, а имя уже
держит живой claim — это почти всегда не второй агент, а перезапуск
прежней сессии. Молча взять то же имя опаснее, чем подождать: файлы
прежней сессии перестают защищаться от конфликтов, а сама сессия
продолжает их править. Никто этого не увидит — просто набор занятых
файлов станет меньше. Правильный путь — имя вида `my-agent/2`.

## Цикл работы агента

```
claim → править → гейты → log-entry → status-set → release
```

Десять шагов, раскрытых в инструкции. Здесь — только те, что обычно
забывают:

**Шаг 2 — снять baseline ДО правок.** Запустите проверки до того, как
что-то меняете. Иначе вы не сможете отличить свою регрессию от чужой.
Это не педантизм: это единственный способ честно сказать «у меня красное»
и не соврать.

**Шаг 10 — всегда `release`.** Даже если задача не удалась. Забытый claim
исчезнет сам через 90 минут, но до тех пор `health-check` будет красным у
всей команды.

## Три вещи, ради которых здесь много комментариев

Комментарии в коде объясняют не «что», а **почему именно так** — и почти
каждый содержит историю поломки, которую предотвращает. Это не
стилистическое решение. Правило, не знающее своей причины, «упрощают» при
первом же рефакторинге.

**1. Красную проверку запускают второй раз.**

Гейт перезапускается один раз. «Красный → зелёный» называется `МЕРЦАНИЕ`,
даёт код 0 и громкое предупреждение в stderr.

Почему: файл правит другой агент прямо во время прогона. Без повтора он
получает «у тебя красный гейт» там, где у него всё зелёное. Через неделю
такого он перестаёт читать результат — и тогда красным станет по-настоящему.

**2. Пропущенная проверка — это не успех.**

Нет входных данных → `SKIP`, и это видно отдельной строкой. Иначе «прогнал
все гейты» неотличимо от «прогнал два из восьми».

**3. Зона не блокирует. Никогда.**

Даже если файл попадает в чужую зону. Единственное, что мешает, — живой
claim на этот файл.

## Что нужно заполнить под свой проект

Шаблон работает сразу после копирования, но чтобы он стал полезным,
заполните в `.agent-protocol.json` четыре вещи:

| Раздел | Что вписать | Зачем |
|---|---|---|
| `zones` | Ваши каталоги верхнего уровня | Чтобы агент за секунду видел границы |
| `verification` | Ваши команды проверок | Чтобы «прогонал гейты» означало что-то |
| `contracts_easy_to_break` | Контракты, которые нельзя ломать | **Самое ценное** — см. ниже |
| `boundaries` | Порты, кэши, глобы, «не коммитить» | Где ломается машина, а не только код |

### Почему `contracts_easy_to_break` — самое ценное

Это единственное место, где написано, что ломать нельзя. Пустой раздел
означает, что каждый агент заново откроет ваши ошибки.

Формат каждой записи: **что это · что ломает · какое действие требуется ·
какой тест это закрепляет.** Последнее обязательно: контракт, не
закреплённый тестом, разрушается в том же коммите, который его нарушил.

```jsonc
"contracts_easy_to_break": {
  "User schema": "Миграции в src/db/migrations/. Изменение набора полей — "
                 "только с новой SCHEMA_VERSION. Закреплено "
                 "tests/test_migrations.py.",
  "-1 sentinel": "-1 в metrics означает «не проверено», а не «ноль»: бюджеты "
                 "проверок общие на прогон. Ранжирование обязано трактовать "
                 "как «неизвестно», иначе неповеренное становится чистым."
}
```

## Проверки (`gates`)

```bash
python scripts\dev.py gates          # все гейты + сводка
python scripts\dev.py gates --list   # только состав, ничего не запускает
```

Четыре свойства, из-за которых раннер и написан:

1. **Не останавливается на первом падении.** Иначе остальные гейты
   остались бы непроверенными, а «прогнал гейты» означало бы «увидел
   первое красное и ушёл».
2. **Красный перезапускается один раз** → `МЕРЦАНИЕ`.
3. **`МЕРЦАНИЕ` ≠ «всё хорошо».** Если падает у вас постоянно — это
   регрессия.
4. **`SKIP` ≠ успех.**

Перед первым прогоном заполните `scripts/gates.json` — в примере половина
проверок ссылается на скрипты, которых у вас ещё нет. `doctor` покажет их
списком, и это лучше, чем узнать из красного вывода:

```
[НЕТ СКРИПТА     ] e2e — сквозная проверка: путь данных от начала до результата

  ЭТИ ГЕЙТЫ НЕ ПРОЙДУТ:
    - e2e: нет scripts/e2e_check.py
    Напишите скрипт, укажите другой путь или уберите гейт.
```

## Дашборд

```bash
python scripts\agent_dashboard.py     # http://127.0.0.1:18900
pip install -e ".[dashboard]"         # нужны fastapi и uvicorn
```

Показывает агентов, занятые файлы, P0/P1, подсказки, последние задачи и
метрики машины.

Он **никогда** не пишет в coordination-файлы. Это не обещание в докстринге —
это проверка, которая сравнивает содержимое файлов до и после обхода всех
эндпоинтов. Второй писатель журнала вернул бы все замороженные правила
single-writer, от которых шаблон и спасает.

Не запущен? Работа продолжается. Это наблюдение, а не инфраструктура.

## Чего шаблон не делает

Честный список, чтобы вы не искали:

- **Не разрешает спор о архитектуре.** Если два агента считают правильными
  разные решения — шаблон не поможет. Для этого `docs/rfc/`.
- **Не заменяет CI.** Гейты локальные. CI ловит регрессию после мержа,
  локальный гейт — до.
- **Не ограничивает число агентов технически.** `claims.max_agents` — это
  договорённость, а не блокировка. И это осознанно: блокировка означала бы
  ровно то зависание, которое шаблон устраняет.
- **Не знает вашего проекта.** Схема данных, API-контракты, модель
  данных — их здесь нет по определению. Их вносите вы.

## Про язык и кодировку

Каталоги считаются UTF-8, читать как `utf-8-sig` — BOM возможен. Русский
текст, сохранённый из cp1251, превращается в мусор, и это лечится:

```bash
python scripts\agent_handoff.py repair-encoding
```

В шаблоне живёт сторож, который ловит двойное кодирование в день
появления файла, а не через месяц. Отдельно он отличает **цитату**
повреждённой строки от **повреждения** файла: агент, который что-то чинил,
вправе привести испорченный пример в записи, и гейт не должен краснеть
из-за чужой цитаты.

**Не пишите файлы через PowerShell 5.1 `Set-Content`** — он добавляет BOM и
перечитывает UTF-8 как cp1251. Пишите средствами Python с
`encoding="utf-8"`. Это стоит одного абзаца и экономит день.

## Тесты

```bash
python -m pytest -q
python -m pytest -q -k universality   # только проверки на «хвосты проекта»
```

`tests/test_template_universality.py` — необычный файл. Он проверяет, что в
коде шаблона **не осталось** чужих путей и команд: любой строковый литерал,
похожий на путь внутри репозитория, обязан разрешаться.

Это страховка от главной болезни шаблонов — незаметно обрасти
проектной спецификой и перестать быть переносимым, оставаясь внешне
похожим.
