# teamwork-agent

Шаблон координации **неограниченного числа параллельных агентов**, работающих
в одном репозитории.

Копируется в любой проект и сразу даёт: протокол взаимодействия, атомарный
инструмент координации, журнал статуса, раннер гейтов, read-only дашборд и
тесты, которые проверяют, что всё это работает.

```
python scripts\agent_handoff.py status          # кто чем занят прямо сейчас
python scripts\dev.py gates                     # все гейты разом + сводка
python scripts\agent_dashboard.py               # http://127.0.0.1:18900
```

Ядро работает на **чистой стандартной библиотеке**. `pip install` не нужен.

---

## Что это и зачем

Проблема, которую шаблон решает, не в том, что агенты плохие. Она в том, что
пять агентов в одном репозитории сталкиваются **молча**.

Типовой инцидент: агент правит файл, который второй агент уже правит. Оба
уверены, что файл их. Через час правки одного перетирают правки другого, оба
записывают в журнал «сделано», гейты зелёные — потому что проверяют уже
испорченный файл. Дедлок выглядит иначе: агент видит «занято», ждёт владельца
зоны, которого нет и не будет, и работа встаёт.

Большинство попыток решить это упирается в одно из двух:

| Подход | Что ломается |
|---|---|
| Зона закреплена за именем агента | Агент ушёл — зона недоступна для всех навсегда |
| Один назначенный владелец журнала статуса | Владелец отключился — журнал замер, отметить claim не может никто |

Шаблон устроен так, чтобы **обе поломки были невозможны конструктивно**:

- **Владение определяется живым claim на конкретный файл, а не именем и не
  зоной.** Зона — подсказка, она никогда не блокирует.
- **Claim без heartbeat 90 минут считается брошенным.** Файлы освобождаются
  сами. Не нужно ждать того, кто не придёт.
- **Журнал self-service:** каждый агент пишет свой раздел, назначенного
  писателя нет.

Третье, менее очевидное: **каждая запись координации атомарна и проходит через
один инструмент.** Правки разных агентов не могут потеряться в гонке, потому
что запись — это `read → modify → atomic replace` с проверкой `mtime`.

## Что внутри

| Файл | Роль |
|---|---|
| `.agent-protocol.json` | **Правила.** Единственный канонический источник |
| `.agent-handoff.json` | **Состояние.** Claims, история задач, подсказки |
| `docs/agent-status.json` | **Снимок.** Кто чем занят, последние гейты |
| `scripts/agent_handoff.py` | Единственный инструмент записи (16 подкоманд) |
| `scripts/dev.py` | Раннер гейтов: не останавливается на первом падении |
| `scripts/gates.example.json` | Образец списка гейтов для вашего проекта |
| `scripts/agent_dashboard.py/.html` | Read-only дашборд |
| `docs/TEAM_PROTOCOL.md` | Механика координации |
| `docs/AGENT_PROMPT.md` | Готовый промпт для нового агента |
| `docs/INSTRUCTIONS.md` | Полная инструкция: перенос, настройка, справочник |
| `docs/PROJECT_STATUS.md` | Шаблон статуса продукта и дорожной карты |
| `docs/rfc/` | Шаблон RFC для решений, которые нельзя принять молча |
| `.gitattributes` | Нормализация переводов строк |
| `tests/` | 183 теста, включая проверку универсальности шаблона, сторож кодировки и сверку чисел в этом README |

Подробная инструкция — **[`docs/INSTRUCTIONS.md`](docs/INSTRUCTIONS.md)**.

## Три команды, с которых начинается работа агента

```
python scripts\agent_handoff.py status                  # что происходит
python scripts\agent_handoff.py who-owns <файл>          # свободен ли файл
python scripts\agent_handoff.py claim <ты> "<задача>" --files <файлы>
```

И цикл работы агента целиком:

```
claim → править → гейты → log-entry → status-set → release
```

## Установка за 60 секунд

```bash
git clone <этот репозиторий> /tmp/teamwork-agent
cd /path/ваш/проект

# 1. Скопировать координационные файлы и инструменты
cp /tmp/teamwork-agent/.agent-protocol.json .
cp /tmp/teamwork-agent/.agent-handoff.json .
mkdir -p docs scripts
cp /tmp/teamwork-agent/docs/agent-status.json docs/
cp /tmp/teamwork-agent/scripts/agent_handoff.py scripts/
cp /tmp/teamwork-agent/scripts/dev.py scripts/
cp /tmp/teamwork-agent/scripts/gates.example.json scripts/gates.json

# 2. Заполнить проектные части протокола (зоны, гейты, контракты, границы)
#    подробности — docs/INSTRUCTIONS.md

# 3. Проверить, что всё живо
python scripts\agent_handoff.py validate
python scripts\dev.py gates
```

Шаблон **копируется**, а не ставится как зависимость: координация — часть
репозитория, она обязана жить в том же коммите, что и код, который она
координирует.

## Установка для нескольких агентов (рекомендуется)

```bash
python -m pip install -e ".[all]"     # pytest, ruff, fastapi, uvicorn
python -m pip install -e ".[dev]"     # только pytest и ruff
```

Ядро (`agent_handoff.py`, `dev.py`) работает без установки вообще.
`fastapi`/`uvicorn` нужны только дашборду.

## Почему здесь так много комментариев

Комментарии в коде объясняют не «что», а **почему именно так**, и почти
каждый содержит историю поломки, которую предотвращает. Это не стилистическое
решение: правило, не знающее своей причины, «упрощают» при первом же
рефакторинге.

Три примера, которые стоит знать до чтения кода:

- **Повтор красного гейта.** Гейт перезапускается один раз, «красный →
  зелёный» называется `МЕРЦАНИЕ` и даёт код 0. Причина: файл правит другой
  агент прямо во время прогона. Без повтора агент получает «у тебя красный
  гейт» там, где у него всё зелёное, и перестаёт читать результат.
- **Зона не блокирует.** Иначе исчезнувший агент блокирует область навсегда.
- **Пропуск ≠ успех.** Гейт без входных данных даёт `SKIP`, а не зелёный
  статус. Иначе «прогнал все гейты» неотличимо от «прогнал два из восьми».

## Тесты

```bash
python -m pytest -q          # весь шаблон
python -m pytest -q -k universality   # только проверки на «хвосты проекта»
```

`tests/test_template_universality.py` — необычный файл: он проверяет, что в
коде шаблона **не осталось** имён, путей и команд проекта-источника. Это
страховка от главной болезни шаблонов: незаметно обрасти проектной
спецификой и перестать быть переносимым, оставаясь внешне похожим.
